# ASCON-KV PROTOCOL (v1)

  ASCON-KV is an end-to-end encrypted, authenticated key-value store
  synchronised across a user's own devices through a blind relay
  server. Its one design idea: once two parties share a key, a secure
  protocol is just an authenticated-encrypted envelope. Every frame —
  request and response, in both directions — is a single Ascon-AEAD128
  seal under a shared key. There are no separate MACs, no signatures,
  no asymmetric crypto, and no plaintext protocol fields beyond the few
  bytes needed to route and decrypt.

  The only primitives are Ascon-AEAD128 (encryption + authentication)
  and Ascon-XOF128 (hashing + key derivation), both from NIST SP
  800-232. All integers are little-endian.

  ## Keys

  A vault is owned by one user across any number of devices sharing a
  single 20-byte RootKey (random). Everything else is derived by XOF
  over an 8-byte domain prefix:

    AEAD_Key = XOF("kv/aead/" || RootKey, 16)   per-entry encryption
    VaultID  = XOF("kv/vid1/" || RootKey, 16)   public routing handle
    AuthKey  = XOF("kv/auth/" || RootKey, 16)   shared channel root

  AEAD_Key never leaves the devices; it keeps the server blind. VaultID
  is public. AuthKey is handed to the server once, at registration, and
  from it both sides derive directional channel keys so that each
  direction has its own key and its own nonce space:

    K_c2s = XOF("kv/c2s0/" || AuthKey, 16)       client -> server
    K_s2c = XOF("kv/s2c0/" || AuthKey, 16)       server -> client

  The server also holds one operator secret, the 16-byte RegisterKey,
  distributed out of band to anyone authorised to create a vault:

    K_reg = XOF("kv/reg0/" || RegisterKey, 16)   registration gate

  A compromise of AuthKey (e.g. a leaky server) permits frame forgery
  against that one vault but never decryption: entry contents stay
  sealed under AEAD_Key, which the server never holds.

  ## Entries

  A vault is an unordered, content-addressed set of self-decrypting
  entries. Each is an independent AEAD seal:

    | ts_ms(8) | nonce(16) | ct_len(2) | ciphertext |
     \________ header, 26 bytes _______/

    ciphertext = AEAD(AEAD_Key,
                      nonce = the header's nonce field,
                      ad    = header = ts_ms || nonce || ct_len,
                      pt    = key_len(1) || key || value_len(2) || value)

  The associated data is the ENTIRE 26-byte header, so the tag binds
  the entry's timestamp, nonce, and declared length: none can be
  altered without failing the open. Binding ts_ms in particular means a
  relay cannot re-date an entry to shift last-writer-wins ordering.
  ct_len is the length of ciphertext (plaintext + the trailing 16-byte
  tag) and is known before sealing, so the whole header is fixed at
  seal time. The plaintext holds only the key and value, and never
  appears outside the ciphertext — the server cannot correlate two
  writes to the same key. A zero-length value is a tombstone (deletion
  of key); empty values are not otherwise stored. The value is opaque to
  the protocol; a client may reserve its leading byte as a format tag
  for its own use (raw, compressed, ...) — a convention that stays
  inside the ciphertext, invisible to the server. See CLIENT.txt.

  Field widths cap an entry so it always fits one frame: key_len is 1
  byte (key is 1..255 bytes), value_len is 2 bytes, and the cleartext
  ct_len is 2 bytes — so a ciphertext, and hence the whole entry, tops
  out near 64 KiB. The marshaled entry (header + ciphertext) MUST be
  under MAX_ENTRY_BYTES = 64 KiB; a value that would exceed that is
  rejected at Put, before it enters the store. So a single entry is the
  largest thing any party must move, and it always fits one frame (see
  Sync).

  ts_ms is the write time in Unix milliseconds; nonce is a 16-byte
  hedged nonce (see Nonces). entry_id is computed on demand as
  XOF("kv/eid1/" || entry_bytes, 16) over the whole entry, giving
  automatic dedup: equal bytes yield equal ids.

  ## Frame

  One envelope carries every message:

    | ver(1) | kind(1) | vault_id(16) | nonce(16) | sealed |
     \_________ header, 34 bytes _____________/

    sealed = AEAD(K,
                  nonce = the header's nonce field,
                  ad    = header = ver || kind || vault_id || nonce,
                  pt    = payload)

  The associated data is the ENTIRE 34-byte header, so the tag binds
  every routing byte — version, kind, vault_id, nonce. A sealed body
  cannot be lifted onto a different header (reassigned to another vault,
  reflected in the other direction, or downgraded) without failing the
  open. The rule is simply "AD = the whole header"; the nonce is also
  the AEAD nonce, so binding it there too is belt-and-suspenders.

  ver is 0x01. kind selects the opening key and, because it is in the
  AD, cannot be flipped:

    0x01 REGISTER   opened with K_reg   (client -> server, first sync)
    0x02 SYNC       opened with K_c2s   (client -> server)
    0x03 RESP       opened with K_s2c   (server -> client)

  vault_id is cleartext because the server must pick a key before it
  can decrypt; nonce is cleartext because nonces are public. The
  payload — everything of substance — is the ciphertext. A frame that
  fails to open is rejected with no side effects.

  Entries pushed in a frame are thus sealed twice: once per-entry under
  AEAD_Key (inner, its AD the 26-byte entry header) and once per-frame
  under the channel key (outer, its AD the 34-byte frame header). The
  outer layer hides entry sizes, counts, and ts_ms from an eavesdropper;
  the inner layer hides contents from the server. Double sealing costs
  one extra Ascon pass over a small body.

  ## Nonces

  Every nonce is hedged so that no single failure causes reuse:

    frame: XOF("kv/rnon/" || VaultID || ts_highres || random16, 16)
    entry: XOF("kv/enon/" || ts_highres || random16, 16)

  random16 (from a cryptographic RNG) provides uniqueness; the
  high-resolution timestamp is insurance against an RNG that repeats
  (fork, early boot). The two cases differ in who generates them:

    Frame nonces have a single generator per key — the client owns
    every K_c2s / K_reg nonce, the server owns every K_s2c nonce — so
    uniqueness is a one-party concern.

    Entry nonces are made under AEAD_Key, which every device shares and
    writes with independently. There is no coordinator, so the random
    component is what keeps writes from colliding across devices, and
    the timestamp hedge covers a device whose RNG has failed — a
    collision here would leak the XOR of two secret values.

  A nonce always travels with its ciphertext (in the frame header, or
  in the entry header); the receiver never recomputes it.

  ## Payloads

  A REGISTER payload just adopts a channel key:

    REGISTER : authkey(16)

  A SYNC payload is one of three ops, all bounded so requests stay small:

    SYNC : op(1) || body
      op 0x00 PROBE : set_hash(16)
      op 0x01 PULL  : cursor(24)              cursor = ts_ms(8) || entry_id(16)
      op 0x02 PUSH  : push_count(4) || entries

  A RESP answers the request that produced it:

    RESP : status(1) || req_nonce(16) || push_count(4) || entries

  entries self-frame via ct_len and appear only in a PULL page (a PROBE
  or PUSH reply carries none). req_nonce echoes the request's frame
  nonce, binding each response to the exact request that produced it, so
  a captured response cannot be replayed against a later one. cursor is
  a 24-byte canonical position (see Sync).

  status lives inside the sealed RESP, so it is authenticated. It is
  reached only once the frame has opened, and is one of:

    0x00 OK          request accepted; a PULL's page (if any) follows
    0x01 DIFFER      PROBE only: the sets differ, walk to reconcile
    0x02 QUOTA       a PUSH would exceed a server limit
    0x03 BAD_REQUEST frame opened but its payload is invalid (e.g. a
                     PROBE carrying entries, or an unparsable entry)

  ## Pre-channel errors

  Some failures occur before the server can seal a RESP at all: the
  frame will not parse, or its seal will not open, so no channel key is
  available to authenticate any reply. In those cases the server
  returns a SINGLE unauthenticated byte and nothing else. A valid RESP
  is a full envelope, so a one-byte reply is unambiguous; the codes sit
  in the 0xE0 range to stay visually distinct from sealed statuses:

    0xE0 BAD_FRAME      header could not be parsed (short / bad length)
    0xE1 BAD_VERSION    unsupported ver
    0xE2 BAD_KIND       unknown kind
    0xE3 UNKNOWN_VAULT  SYNC for a vault_id with no registration; the
                        client should REGISTER. This cannot be a sealed
                        status — with no registration there is no
                        AuthKey to seal under.
    0xE4 BAD_AUTH       the seal did not open: wrong RegisterKey on a
                        REGISTER, or wrong AuthKey / forgery on a SYNC.
                        (A SYNC that fails to open cannot be answered
                        authentically either, since the sender's key
                        does not match the one a RESP would use.)
    0xE5 TRY_LATER      transient refusal (e.g. overload); retry later

  These bytes are hints, not proofs: an on-path attacker can forge or
  drop them. A client uses them only to choose local behaviour —
  REGISTER on UNKNOWN_VAULT, back off on TRY_LATER, surface a failure
  otherwise — and NEVER to mutate vault state. This is safe because no
  pre-channel byte triggers a state change: the worst a forged one can
  do is delay a sync or provoke an idempotent re-registration, and the
  re-registration reveals nothing, since it reseals AuthKey under K_reg
  which the forger does not hold.

  ## Sync

  Reconciliation is a cheap equality probe backed by a paged walk.
  Every request and every response stays small — the heavy data moves a
  bounded page at a time — and the server keeps no session: it answers
  only "entries after this cursor" and "add these", both stateless.

  Set fingerprint. Either party hashes its whole set:

    SetHash = XOF("kv/sset/" || u32(N) || concat(entry_ids in
              canonical order), 16)

  where canonical order is (ts_ms asc, entry_id asc) and N is the count,
  bound in. Two parties agree on SetHash iff they hold identical sets
  (up to a negligible collision). SetHash is the single "are we done"
  oracle: a PROBE that matches means fully in sync.

  The three ops behave as:

    PROBE(set_hash)  OK if the server's SetHash matches, else DIFFER.
                     Fixed-size, independent of vault size.
    PULL(cursor)     the next whole entries in canonical order strictly
                     after cursor that fit the page budget PAGE_BYTES —
                     at least one, since every entry is < MAX_ENTRY_BYTES
                     <= PAGE_BYTES. An empty page means the server holds
                     nothing beyond cursor.
    PUSH(entries)    the server adds any it does not already hold
                     (idempotent, content-addressed) and acks.

  The client loop:

    1. PROBE. If OK, done.
    2. Otherwise walk a suffix window anchored a look-back delta below
       the client's frontier — the newest canonical position in its
       store:
         - PULL forward from (frontier.ts_ms - delta, 0) a page at a
           time, COMMITTING each page to the log before the next
           request. Committing advances the frontier, so the next
           cursor is re-derived from the store: the client keeps no
           cursor in RAM, and a crash mid-walk simply resumes from the
           log.
         - PUSH the client's own entries over the same window, a page at
           a time. This is dedup-tolerant — the client re-sends the
           window's overlap and the server drops what it already holds,
           so the client needs no record of what the server has.
    3. PROBE again. If OK, done. If still DIFFER the divergence lies
       below the window: grow delta (geometrically) and repeat from 2.

  delta is purely client-local — it never appears on the wire and is no
  server state, only which cursor the client chooses to send. Anchoring
  the walk delta below the frontier re-examines recent history on every
  attempt, so a concurrent or lightly-backdated write that landed behind
  the frontier is caught without a full walk; growing delta reaches an
  anchor of zero, a full walk that always converges. Both extremes are
  valid and fully interoperable, since the server never sees delta: a
  client MAY anchor at zero on every reconcile (simplest, but rescans the
  whole set each time), or window and widen. The reference client does
  two things. After a local write it takes a fast path: it PUSHes just
  the entries it created since the last sync and PROBEs — a match ends
  the sync with no pull and no walk, so writing one key moves one entry
  regardless of vault size. Otherwise (a plain sync, or when that probe
  still differs) it windows: round 0 looks back a fixed recent span
  below its frontier and widens to a full walk if a PROBE still differs.

  Why it converges: a PULL walk to an empty page leaves the client
  holding every server entry in the window, and the dedup-tolerant PUSH
  leaves the server holding every client entry in the window. If the
  window spans the whole divergence the next PROBE matches; if not, a
  wider one does, and anchor zero spans everything. Every step is a
  bounded, log-committed page, so an interrupted sync loses nothing and
  resumes from a more-complete store. The only transient client state is
  delta, which is safe to lose — a restart just re-widens from the
  frontier.

  Recovery is the same loop at anchor zero, not a distinct mode. A fresh
  or wiped client has frontier zero, so its first walk is a full pull
  that rebuilds it from the server; a wiped server is rebuilt from the
  client's full-window PUSH. In steady state the PROBE matches and
  nothing else is sent.

  ## Registration

  The first frame for a VaultID is a REGISTER sealed under K_reg,
  carrying the AuthKey the server is to adopt. The server opens it with
  its own K_reg — a bad RegisterKey means the seal will not open, which
  IS the authorisation gate — records AuthKey for vault_id, and acks
  under K_s2c. The client then syncs normally over the channel keys.
  There is no permissionless registration.

  Re-registration is idempotent: a device presenting an AuthKey that
  matches the stored one is accepted, a mismatch rejected. A server that
  lost its state but kept RegisterKey lets any RootKey+RegisterKey holder
  re-register under the same AuthKey and resume.

  ## Merge

  A device's view is derived by decrypting every entry and replaying it
  in canonical order under last-writer-wins: a non-empty value installs
  (key, value), an empty value removes the key. Replay is idempotent,
  so any two devices holding the same set compute the same view. An
  entry that fails to open under AEAD_Key is silently discarded — never
  fatal, and not re-added on later syncs since it simply fails again.

  ## Quotas

  Per vault the server enforces MAX_ENTRIES, MAX_VAULT_BYTES, and
  TS_SKEW_MS (|ts_ms - now|, default 24h); it may cap MAX_VAULTS. The
  page budget PAGE_BYTES — the most a frame's payload may carry — MUST
  be at least MAX_ENTRY_BYTES plus frame overhead, so any one entry fits
  a single frame; paging then decouples vault size from the body cap, a
  frame never carrying more than one page. Skew and quota are checked
  only against entries the server does not already hold, so re-pushing
  an accepted entry is a no-op and is never re-judged. A violation
  rejects the offending frame (QUOTA or BAD_REQUEST) so a pusher cannot
  mix valid and invalid entries in one PUSH.

  ## Pairing and rotation

  A device joins by receiving the RootKey out of band as Crockford
  base32 (32 chars, no padding bits -- displayed as 8 groups of 4);
  the RegisterKey travels the same channel (26 chars). The new device derives VaultID, AuthKey, and the channel keys
  and registers. Rotation is out of band: to retire a device, generate
  a fresh RootKey on a trusted device and re-pair the others. The old
  vault becomes abandoned storage the retired device can still read but
  not influence, ageing out under quota. There is no in-band ratchet: a
  deterministic one would hand the old key's holder the new key, and a
  random one would still need the pairing channel to carry the entropy.

  ## Transport

  Any reliable transport. On the wire a frame exposes only ver, kind,
  vault_id, nonce, and its size and timing; the op, cursors, set_hash,
  entry sizes and counts, ts_ms, status, and the AuthKey at registration
  are all sealed. TLS is therefore optional and buys only the remaining
  metadata (which vault, when, how big); the catastrophic leak — an
  AuthKey captured in cleartext, enabling forgery — cannot happen.
  Clients MUST set a request timeout and cap each response body to one
  page.

  ## Notes

    1. The only durable secret a device must protect is the RootKey.
    Every other local file is a rebuildable cache.

    2. The server sees ciphertext sizes, timestamps, and per-vault
    write rates — never plaintext keys, values, device identities, or
    user count.

    3. Steady-state polling is a fixed-size PROBE and reply. A change
    costs a bounded paged walk of the recent window, not the whole
    vault; only a fresh or wiped party, or a divergence backdated below
    the window, widens toward a full walk — and even that moves one
    page at a time, committing as it goes.

    4. A client bounds its own sync. The PROBE/reconcile loop has a
    round budget, and a PULL walk requires the cursor to advance
    strictly on every page — a server that never returns an empty page,
    or replays a non-advancing one, is rejected rather than looped on.
    A misbehaving or hostile relay can stall availability but cannot
    hang the client, and (per §Merge and the double seal) can never
    corrupt or read its data.
