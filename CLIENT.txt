# ASCON-KV CLIENT CONVENTIONS

  This documents conventions of the reference ASCON-KV client that sit
  ABOVE the wire protocol (PROTOCOL.txt). The server neither sees nor
  depends on any of them — they describe only how a client encodes data
  inside the opaque, encrypted entry value. Two clients interoperate on
  a vault only if they share these conventions.

  ## Value encoding

  A non-empty entry value is:

    value = fmt(1) || payload

  fmt names the payload's encoding; the client strips it on read and
  returns payload. It lives inside the entry ciphertext, so it is
  invisible to the server and adds nothing to what the wire exposes.
  value_len counts fmt plus payload.

    0x00        raw — payload is the value verbatim
    0x02        reserved: KV document — payload is a sequence of
                typed key-value entries in the Quietcasting KV
                encoding (qcrf SPEC.t, section KV container). The
                ecosystem's one structured codec; a vault value
                that needs named, typed fields uses this rather
                than a new encoding. Unspecified until its first
                consumer arrives; reserved here so nothing else
                takes the code point.
    0x01, 0x03..0xFF  reserved for future encodings (e.g.
                compression). A reader that does not recognise fmt
                treats the value as opaque and does not decode it.

  Tombstones are unaffected: a deletion is the protocol's empty value
  (value_len = 0, no fmt byte). The fmt byte appears only in non-empty
  values — so a present-but-empty logical value is fmt || (empty
  payload), value_len = 1, which is distinct from a tombstone.

  ## Compression is a security decision

  Should a future fmt compress the payload, compress the plaintext per
  value before the entry is sealed — never at the frame layer, where
  sealed entries are already incompressible. Compress-then-encrypt
  leaks through ciphertext length (the CRIME/BREACH class): the server
  already sees each value's length, and compression makes that length
  reveal how compressible, hence something about the content of, the
  value. For a secrets vault, enable it deliberately, consider
  length-padding sensitive values, and never compress a value that
  mixes untrusted input with a secret.
